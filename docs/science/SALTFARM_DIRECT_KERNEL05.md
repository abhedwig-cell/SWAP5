## Implementation and state ownership

`app/hybrid_water/direct_day_kernel.f90` calls the existing model resolver,
`kernel_executor_t`, reference-floor sampler and commit operation. Each factory
allocates its own context, model, committed-column states and refusal flags;
there is no global handle registry or shared mutable model state. The Python
owner releases that context. A watchdog marks cancellation without freeing
Fortran memory from its timer thread.

Before the donor advances, the direct request checks column ownership and the
committed clock. After the typed reply arrives, the unchanged executor clones,
samples, checks mass and commits or refuses it. This removes a process and2922
kernel input writes plus2922kernel reply reads over1461days; it does not bypass
SWAP5 acceptance. Existing day messages/logs remain available through a local
transport facade. The prepared total stock is passed exactly, rather than
recomputed with a different summation order in the bridge.

Selection is limited to the registered, nonexperimental macro-free SaltFarm
application. Other application routes retain their process transport. The existing
external `CoupledDailyColumn` route also retains its process transport and passes
its actual discard/replay and independent-column controls. No broader direct-ABI
or external-C-API qualification is claimed. Original donor Fortran source files
and the projected-budget source are byte-identical to the admitted prior build.
No physics, process order, numerical iteration policy or tolerance changes.

Build metadata binds bridge source, Python owner source, native library, compiler
