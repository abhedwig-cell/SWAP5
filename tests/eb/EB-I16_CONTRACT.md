Decision:

`DESIGN_FROZEN_NO_PRODUCTION_IMPLEMENTATION`

EB-I16 freezes only the generic runtime/coupler contract by which a later production implementation may supply liquid-water donor temperature for an already-selected EB-I13 bottom thermal sample whose donor class is external. EB-I16 changes no production source, creates no new water-transfer authority, commits no energy and introduces no MODFLOW-specific or deep-vadose-specific type into SWAP.

## Problem inherited from EB-I15

EB-I15 can evaluate all thermally complete local-outflow samples and exact-zero samples. For nonzero inward bottom water, EB-I13 correctly identifies the donor as external but intentionally carries no external donor temperature. EB-I15 therefore fails closed and exposes no complete bottom sensible-energy total.

The missing capability is not another enthalpy law. The missing capability is explicit ownership and provenance for the external liquid-water temperature at the energy quadrature point belonging to the same accepted transfer sample.

## Ownership boundary

The EB-I13 candidate remains the sole SWAP-side authority for the accepted bottom water transfer, its sign, its accepted-route sample order and its interval partition.

An external thermal provider is never a water-mass authority. It shall not create, replace, correct, rescale, accept, reject or commit `Q_b`. Any water-transfer value carried in a provider request is read-only context copied from the current EB-I13 sample and can never override the candidate value used by the energy evaluator.

The external thermal provider owns only the statement: for this exact accepted external-donor request, a finite donor temperature with explicit provenance is or is not available.

## Candidate-scoped synchronous request model

The frozen reference composition is request-driven rather than a free-standing temperature array.

A later evaluator traverses the actual immutable EB-I13 candidate. Only when the current sample satisfies all of the following shall it issue an external donor request:

- `donor_class == FMR_BOTTOM_THERMAL_DONOR_EXTERNAL`;
- `bottom_outward_exchange_native < 0` exactly;
- the candidate and sample are otherwise valid.

No request is issued for local outflow or exact-zero transfer.

The reference request is synchronous and candidate-scoped. This prevents a stale temperature array from being silently attached by position to a different accepted route. A future batched implementation is allowed, but it must preserve exactly the same request/response identity semantics.

## Minimum request identity

A later production request contract shall contain at least:

- an evaluation-scoped opaque token generated by runtime/composition, positive and nonpersistent;
- the accepted sample ordinal within the current candidate;
- the sample `t0` and `t1` copied from the candidate;
- the current accepted `bottom_outward_exchange_native` copied as read-only context;
- the required energy quadrature time.

For the EB-I14 current-reference discretization, the required external donor-temperature quadrature point is `t1` of the accepted sample.

The request token and sample ordinal identify the live evaluation operation. `t0`, `t1` and the contextual transfer provide semantic cross-checks. None of these fields creates a second mass ledger or a persistent per-column identity store.

## Minimum response semantics

A later provider response shall contain at least:

- the same evaluation token and sample ordinal as the request;
- an explicit availability/completeness flag;
- a finite donor liquid-water temperature in degrees Celsius when complete;
- an opaque positive provenance/source identity;
- a nonnegative provenance/source revision or equivalent immutable version marker.

The response shall not contain an authoritative replacement water transfer.

A provider may internally derive the temperature from groundwater, a deep-vadose transfer component, a prescribed boundary source or another component. That source-system mapping belongs to runtime/coupler composition. SWAP does not know the external component type.

## Temporal semantics

EB-I14 froze the current-reference bottom-water/energy rule around accepted model advances. Local outflow uses the terminal local donor temperature paired with the terminal-flux water rectangle. The external binding shall therefore request donor temperature at the same sample quadrature point, `t1`.

How an external component obtains a temperature at `t1` is outside SWAP. It may expose a native state at `t1`, interpolate a qualified external trajectory or use a constant prescribed temperature. That adapter-side temporal mapping must be independently qualified. SWAP shall not invent an interpolation rule, average endpoint temperatures, reuse a previous temperature or substitute the local bottom-soil temperature.

A future higher-order jointly qualified water/temperature quadrature remains possible behind a later versioned contract. It is not silently introduced by EB-I16.

## Fail-closed rules

For any nonzero inward sample, complete bottom sensible-energy evaluation is unavailable if the external response is absent, explicitly unavailable, nonfinite, stale, token-mismatched, ordinal-mismatched or semantically inconsistent with the current sample.

There is no local SWAP temperature fallback, no zero-enthalpy fallback, no previous-sample fallback and no silent default external temperature.

This incompleteness does not retroactively reject or alter an otherwise valid mass-conserving hydrologic transaction under the current restricted-thermal architecture. It only makes complete bottom sensible-energy publication ineligible.

## Energy evaluation after successful binding

When and only when the external response is complete and valid, the existing EB-I15/EB-I04 law applies without modification:

`E_i = 0.01 * rho_w * c_p_w * Q_i * (T_external,i - T_ref)` [J/m2].

`Q_i` is read from the EB-I13 candidate, not from the provider. Since inward water has `Q_i < 0`, a donor warmer than `T_ref` contributes negative outward-positive sensible energy, meaning sensible energy enters SWAP.

EB-I16 creates no new energy formula and no new sign convention.

## Transaction, commit and rollback boundary

The external binding is candidate-scoped metadata. It is not continuation state and is not part of F-KT restart state.

A failed or abandoned outer candidate shall not publish an accepted energy record derived from its provider responses. The provider response itself cannot authorize hydrologic acceptance, physical commit or accepted energy publication.

A later implementation may cache provider answers within one evaluation/worker for efficiency, but rejected or superseded candidate bindings must not leak into another accepted route.

Accepted energy commit/publication remains a separate transactional integration boundary.

## Coupling and component-composition boundary

The existing `mod_groundwater_coupling_contract` remains the authority for direct groundwater interface head/flux convention and its own coupling lineage. EB-I16 does not modify or duplicate that contract.

A groundwater coupler may use its own valid coupling lineage to construct or validate opaque external-temperature provenance. A deep-vadose component may use a different lineage mechanism. The SWAP energy evaluator shall depend only on the generic external thermal provider seam, not on `groundwater_interface_lineage_t`, MODFLOW cell identity, tile fractions or deep-vadose routing.

This preserves direct coupling, transfer-zone coupling and other future external components behind one SWAP-side thermal request contract.

## MultiSWAP and performance boundary

The contract permits both scalar synchronous lookup and batched provider evaluation. A batched implementation may collect external requests across many columns or samples, provided responses remain exactly matched to their originating requests.

No permanent temperature history is required per column. No provider object is required for columns/candidates with no external inward sample. No extra Richards or soil-temperature solve is permitted merely to recover external donor temperature.

Provider cost and diagnostics must be attributable so problem external sources do not silently serialize or stall large MultiSWAP batches.

## Diagnostics

A later implementation shall make at least these states distinguishable:

- no external donor required;
- external donor requested and complete;
- external donor unavailable;
- invalid/nonfinite external temperature;
- request/response identity mismatch;
- provenance/revision invalid or stale.

Diagnostics shall not masquerade incomplete energy as a complete zero.

## Relationship to the thirty architecture invariants

EB-I16 is deliberately outside kernel physics state. It preserves one kernel, kernel/I-O separation, compact committed state, worker-local scratch, transaction semantics, generic time, flexible coupling windows, strict mass conservation, scalable MultiSWAP composition, optional deep-vadose ownership outside SWAP, alternative soil-water solvers, physics/numerics separation and explicit runtime diagnostics.

The detailed invariant-by-invariant disposition is recorded in `tests/eb/EB-I16_ARCHITECTURE_AUDIT.json`.

## Hard nonclaims

EB-I16 does not qualify production implementation of the provider seam, a MODFLOW temperature interface, deep-vadose thermal physics, external-component temporal interpolation, accepted energy commit/publication, energy-ledger restart, advective-energy feedback into the governing soil-temperature solve, internal soil-face advective heat transport, higher-order temporal energy accuracy, a closed soil/land-column energy balance or canonical admission.

## Next implementation gate

A subsequent implementation workunit may implement the frozen seam only if it proves all of the following: request creation occurs only for valid nonzero external-donor samples; local and exact-zero samples never query the provider; the provider cannot alter candidate water transfer; complete responses are bound to the live request and exact sample; missing, stale, mismatched or nonfinite responses fail closed; the quadrature request time is the current-reference sample `t1`; no local or default temperature fallback exists; external energy uses the candidate `Q_i` and existing EB-I04 law; rejected/superseded candidate bindings cannot leak across routes; no persistent per-column temperature history is introduced; no extra physical solve is performed; batching preserves request identity; hydrologic mass/transaction/restart owners remain unchanged; and `-O0`/`-O2` plus the full thirty-invariant audit remain qualified.
